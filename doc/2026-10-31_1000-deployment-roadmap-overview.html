McApp · DK5EN · planning overview · 2026-10-31 · status: ideation, backlog B11 to B13, B15

McApp deployment roadmap

Today McApp installs in one way only: a headless Raspberry Pi with the Lite image, driven by mcapp.sh. Three backlog items widen that. Bigger Pis with a desktop become valid hosts, McApp ships as a container image for NAS owners and admins, and the Bluetooth part becomes a small native service that any Linux box in the LAN can run and McApp can find on its own.

01 · At a glance

Three initiatives, one goal: more places to run McApp

B11 · desktop-image-gate

Pi 4/5 with a desktop

bare metal · bootstrap only
  • The hard "desktop detected, abort" rule becomes a RAM rule.
  • Under 1 GB refuse, 1 to 2 GB ask, 2 GB and more install.
  • Zero-2W memory tuning is skipped on desktop boxes, so the GUI keeps working.

Output: changed mcapp.sh + one new test suite

B12 · container-deployment

McApp as a container

Alpine · GHCR · Traefik
  • One small Alpine image: the web app, API and live stream in one process.
  • Published to ghcr.io/dk5en/mcapp for arm64 and amd64.
  • Database in a volume; updates by pulling a new image tag.

Output: image, compose example, CI workflow

B13 · ble-service-and-lan-discovery

BLE service anywhere, found automatically

native · mDNS · pairing
  • mcapp-ble installs on any Linux box with a Bluetooth adapter.
  • It announces itself in the LAN; McApp lists it in Settings.
  • Pair once with a key; only one McApp owns the radio link at a time.

Output: installer script, discovery, Settings panel

04 · B11 · Desktop image gate

Bigger Pis may keep their desktop

Today any desktop package aborts the install, which protects the 512 MB Zero 2W but locks out a Pi 4 with 4 GB. The new gate decides on real memory, and a saved profile decides which memory tuning runs, so the GUI is not crippled by settings meant for a headless Zero.

Output: changes in bootstrap/mcapp.sh and bootstrap/lib/*.sh, a new bootstrap test suite, no app code. Four waves: detection, profile gating, revert path, tests. No system-epoch bump is planned, because nothing changes for existing headless boxes.

05 · B12 · Container deployment

One Alpine container, the radio stays outside

The container holds McApp and nothing else. TLS and the login live in a reverse proxy you already run, the database lives in a volume, the Bluetooth radio lives in a native service on a real host. Only the UDP port from the node goes straight into the container.

06 · B12 · The UDP path

The one networking trap: the node's address

McApp learns where the node is from the first UDP datagram it receives. Normal rootful Docker keeps the sender's address, so this just works. Some setups replace it with Docker's own gateway address, McApp learns the wrong target, and every message it sends goes nowhere.

  • Point the node at the host. The node's EXT-UDP IP is the Docker host's LAN address, not the container's.
  • Port 1799 cannot move. The firmware sends to a compile-time EXTERN_PORT. That means one McApp per host IP; a second instance needs its own LAN IP (macvlan).
  • Outgoing frames leave from a separate socket on a random port and are translated to the host's address; the node accepts that.
  • Platform list: wave 0 tests Pi Docker, Synology, QNAP, Unraid and rootless Podman before any platform is called "supported".
07 · B12 · Web access

Behind Traefik or behind your own proxy

Both paths are first-class. Many home servers already run nginx, Caddy or Nginx Proxy Manager with a login in front of everything, plus other web services on the same box.

Traefik with labels

  • Router with a Host() rule on the websecure entry point, cert resolver for TLS.
  • An ipallowlist on the real LAN range, never Docker's 172.16.0.0/12.
  • Optional basicauth or forwardauth middleware for the login.
  • No buffering on the live stream (flushInterval).

Your own reverse proxy

  • Publish the container port on loopback with any free host port: 127.0.0.1:8085:2981.
  • The login must cover every path, /api/ and /events included.
  • Browser tabs: Basic auth works. Installed iPhone app: no Basic auth; a login page on the same origin with a session cookie.
  • nginx: proxy_buffering off for the live stream.

Rules that hold either way

  • McApp's API has no login of its own; the proxy is the gate.
  • Node Admin stays LAN-only even behind a login.
  • Host network mode: set MCAPP_PORT if 2981 is taken, bind to loopback or LAN IP.
  • Logs rotate in compose (10 MB x 3) so a NAS disk does not fill.
services:
  mcapp:
    image: ghcr.io/dk5en/mcapp:latest        # or :v2.2.0 to pin, :dev for pre-releases
    restart: unless-stopped
    read_only: true
    tmpfs: [/tmp]
    environment:
      TZ: Europe/Berlin
      MCAPP_BLE_URL: http://192.168.1.20:8081    # native BLE service; an IP, .local does not resolve in Alpine
      MCAPP_BLE_API_KEY: ${MCAPP_BLE_API_KEY}
    ports:
      - "1799:1799/udp"                      # node EXT-UDP, fixed port
      # - "127.0.0.1:8085:2981"              # only for your own proxy instead of Traefik
    volumes:
      - mcapp-data:/var/lib/mcapp            # whole directory, never just messages.db
    labels:
      traefik.enable: "true"
      traefik.http.routers.mcapp.rule: Host(`mcapp.home.arpa`)
      traefik.http.routers.mcapp.middlewares: mcapp-lan
      traefik.http.middlewares.mcapp-lan.ipallowlist.sourcerange: 192.168.1.0/24
      traefik.http.services.mcapp.loadbalancer.server.port: "2981"
    logging:
      driver: json-file
      options: { max-size: 10m, max-file: "3" }
volumes:
  mcapp-data:

08 · B12 · Build and registry

Where the images come from

The release process stays as it is. A GitHub Actions workflow reacts to every published release, builds the image from the same tarball the Pis install, and pushes it to the GitHub Container Registry under the McApp repository.

ReleaseGit tagImage tags on GHCRWho should use it
ProductionvX.Y.Z:vX.Y.Z · :X.Y · :latesteveryone; pin :vX.Y.Z for full control
Dev pre-releasevX.Y.Z-dev.N:vX.Y.Z-dev.N · :devtesters; :dev moves with every pre-release
  • Platforms: linux/arm64 (Pi 3/4/5 with 64-bit OS) and linux/amd64 (NAS, PCs). 32-bit armv7 is an open question.
  • Size: target 60 to 80 MB compressed pull, roughly 90 to 110 MB on disk (estimate).
  • Base: python:3.13-alpine, multi-stage with uv; every dependency has a musl wheel or is pure Python once timezonefinder is left out.
  • Version shown in the app comes from MCAPP_VERSION, set from the tag; without it a dev image would claim the plain release number.
09 · B12 · Persistence

Everything worth keeping lives in one volume

File in /var/lib/mcappContentLost without the volume
messages.db + -wal, -shmall messages, positions, ACKs, settingsthe whole history
runtime.jsonlearned node IP, callsign, positionMcApp forgets where the node is
secret.keykey for stored passwordsQRZ, Node Admin and feed passwords
vapid.jsonWeb Push keypairevery push subscription
Local disk only. SQLite in WAL mode needs shared memory and real file locks. A database volume on NFS or SMB, the usual NAS reflex, corrupts or loses writes. Mount the whole directory, never only messages.db. Backups run online through Python's sqlite3 module inside the container; no stop needed.

Moving from a Pi: stop McApp, copy messages.db, runtime.json and vapid.json into the volume. Push subscriptions survive. Stored passwords do not: the Pi's key is bound to its board serial, so QRZ, Node Admin and feed passwords are entered once more.

10 · B13 · BLE service and discovery

The radio link as a small service you can place anywhere

The Bluetooth adapter has to be near the node, while McApp can sit on a NAS in the basement. The BLE service bridges that gap: it runs natively on whatever box is close to the node, announces itself in the LAN, and McApp picks it up in Settings.

Pairing in Settings

  1. Open Settings, McApp scans the LAN for 15 seconds.
  2. Pick a BLE service from the list, or type a URL.
  3. Paste the key the installer printed on that box.
  4. McApp checks /health (version, API level) and claims the link.

Security changes

  • The BLE service refuses to listen on the LAN without a real API key.
  • Changing the BLE target in McApp is LAN-only and forces the key to be entered again.
  • The key is never shown back by the API.
  • One owner at a time; taking over is an explicit button.

Containers and discovery

  • Multicast does not cross Docker's default bridge network.
  • Options: host network, macvlan, or announce through the host's avahi.
  • Otherwise: manual URL, which is enough for a fixed setup.

12 · Debated

Ansible, nginx, a Debian package: considered

Ansible instead of mcapp.sh

decision: keep bash
  • The install has no controller: one curl | sudo bash on a fresh Pi.
  • Updates run the installer on the box itself, so Ansible would run locally with its full footprint (60-100 MB per run, estimate) on a 415 MB Zero.
  • The hard parts (WiFi safety, detached apt, ramlog, config.txt rules) would become shell tasks in YAML anyway.
  • Instead: shellcheck in CI and tests for the untested libs.

nginx instead of uvicorn

decision: no
  • uvicorn runs the Python app; nginx cannot replace it, only sit in front.
  • In the container the operator's proxy already does TLS, compression and login.
  • On bare metal nginx would lose Caddy's automatic certificates.

Debian package via apt

decision: BLE first
  • Needs a signed APT repository per Debian release and architecture.
  • dpkg knows one version: the slot system and instant Activate rollback go away.
  • System tuning stays in mcapp.sh --converge, never in maintainer scripts.
  • First .deb: mcapp-ble. Decide on McApp after the container ships.

B15: drop lighttpd

new backlog item
  • lighttpd only serves static files behind Caddy.
  • Caddy already has file_server; serving the SPA there removes a process from the Zero.
  • Measure the memory win first; needs an epoch bump.
13 · Decisions

Questions answered on 2026-10-31

  1. Memory thresholds. Live on mcapp.local: the McApp stack uses about 120 MB RSS (mcapp 73, BLE service 24, Caddy 18) of 474 MB. Refuse below 800000 kB, confirm below 1700000 kB; one real 1 GB and 2 GB reading still wanted. Desktop boxes skip both RAM disks (/tmp and /var/log). B11
  2. Desktop detection. mcapp.local and rpizero both boot to multi-user.target with no display manager. No Armbian in the fleet; the display-manager rule stays as a safeguard. B11
  3. Platforms. 64-bit only. Supported: rootful Docker (Pi OS, Debian, Ubuntu), Synology, QNAP, Unraid with host network as fallback, rootful Podman. Conditional: rootless Podman on pasta. Unsupported: rootless Docker (builtin driver), rootless Podman bridge networks. B12
  4. GitHub Actions. Enabled and the repo is public; only the tests workflow is switched off. Public repos get free runners, native arm64 runners and free GHCR storage. Fallback: local docker buildx in release.sh. B12
  5. GPS card on a failing /api/timezone. No visible breakage, but it retries on every GPS update and logs a client error each time: small webapp fix, and the backend must return 501 explicitly. B12
  6. iPhone app behind a login. No Basic auth: the installed app does not show the prompt. Use a login page on the same origin with a session cookie; device test in wave 0. B12
  7. avahi and libnss-mdns. Added as bootstrap dependencies. Zero RAM impact: both already run on mcapp.local and rpizero. B13
  8. Installing the BLE service. uv tool install from the repo subdirectory should work after an entry-point fix and a package rename; the decided route is a Debian package for mcapp-ble. B13
